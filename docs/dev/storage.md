# Storage package (`@relic-bridge/storage`)

The only way core, auth and http-app reach persistence (ADR-0006). `src/` uses web-standard APIs only (ADR-0004);
runtime-specific code lives in the adapters' hosts (P2-02 Node SQLite, P3-02 D1).

## Entry points

| Import | Contents |
|---|---|
| `@relic-bridge/storage` | `Storage` interface and record types, errors, `createMemoryStorage`, `createYamlStorage` / `yamlRecords` / `parseYamlConfig` (+ the YAML zod schema), `migrate` / `MIGRATIONS`, row rules (`validate.ts`), `newId()` |
| `@relic-bridge/storage/d1` | `createD1Storage(db, { now, migrate })`, `d1MigrationDriver`, `mapD1Error` and the structural `D1DatabaseLike` type (Workers; P3-02) |

| `@relic-bridge/storage/testing` | `runStorageContract()`, fixtures (test-only; imports vitest) |

## The `Storage` interface

`src/types.ts`. Async repositories: `users`, `credentials`, `projects`, `grants`, `accessTokens`, `auditLog`,
`settings`, `kv`, `grantUsage`, plus `kind`, `readOnly`, `close()` and the optional `loadAccessRecords` (SQL adapters, see below).

- **Ids** are generated by the caller (`newId('cred')`), because a credential id is part of its encryption AAD
  (ADR-0007) and must exist before the row.
- **Times** are epoch milliseconds; adapters stamp `createdAt` / `updatedAt` with their clock (`now` option).
- **Records** come back frozen and copied; mutating input after a call never changes stored state.
- **Lookups** return `null` for a missing row; **updates/deletes** of a missing row throw `NotFoundError`.
- `ConflictError` = unique or referential rule (duplicate id/slug/email/identity/token hash, unknown reference,
  deleting a credential still in use). `InvalidInputError` = row rule (`validate.ts`, mirrored by the schema's CHECK
  constraints). `ReadOnlyStorageError` = write on the `yaml` adapter.
- `null` in a grant's `tools` / `accountIds` means "no further restriction"; `[]` means "nothing". Same for a
  project's `enabledTools` (`null` = all built-in read-only tools).

### Secrets

- Credentials: `key` is `{ kind: 'encrypted', ciphertext, iv (12 bytes), keyVersion }` in every writable adapter.
  `keyHint` holds at most the last 4 characters for display. Encrypt and decrypt only through
  `Keyring.encryptCredentialKey` / `decryptCredentialKey` in `@relic-bridge/auth` (P2-03, [secrets](../guide/secrets.md)).
- `credentials.update(id, { key, ifKey })` is a compare-and-swap: with `ifKey` the patch applies only while the stored
  key is still exactly `ifKey` (ciphertext, IV, version), else `ConflictError` (`credentials.key`). SQL adapters must
  check it inside the `UPDATE` statement, not with a separate read. Master-key rotation relies on it.
- `settings.setIfAbsent(key, value)` is an atomic insert-if-absent (`true` when this call wrote the value). SQL
  adapters use `INSERT … ON CONFLICT(key) DO NOTHING`. Key check values are registered with it (P2-06, SR-4).
- The `yaml` adapter yields `{ kind: 'env', variable }` or `{ kind: 'inline', reveal() }` instead; `reveal` is
  non-enumerable, so a credential serialises without the literal.
- Access tokens: only `tokenHash` (SHA-256, lowercase hex) and a display `prefix` (≤ 12 chars). Format and hashing
  are P2-05.
- Audit: append-only (`append`, `list`, `purgeBefore` for retention, and read-only `stats`, one bounded aggregate over `tool_call` rows: window at most 90 days, at most 100 groups; the SQL is shared by the SQLite and D1 adapters in `audit-stats.ts`). `list` pages by `beforeId` (keyset on the primary key: constant cost per page, verified on 100k rows). Callers mask NRQL before `append` (P2-08).

### Grant usage (quota counters, P7-12)

`grants.quota` (JSON, null = unlimited, `StoredQuota`: `day` / `month` caps on `queries` and `inspectedEvents`,
`warnPercent`) is a grant column; the counters are the `grant_usage` table, one row per `(grant_id, period)` with
`period` = `d2026-10-06` (UTC day) or `m2026-10` (UTC month), cascading with the grant (`usagePeriods`, `periodResetsAt`
in `usage.ts`). `Storage.grantUsage` is atomic, every method one statement (`USAGE_*_SQL`, shared by SQLite and D1):

- `reserve(grantId, period, maxQueries | null)`: `INSERT ... ON CONFLICT DO UPDATE SET queries = queries + 1 ... WHERE ? IS NULL
  OR queries < ? RETURNING`, so the cap check and the increment are one write and concurrent callers cannot exceed
  `maxQueries`; resolves the new counters, or `null` (nothing changed) at the cap. The contract suite runs 50 concurrent
  reserves against a cap of 10 and expects exactly 10 successes, on memory, SQLite and D1.
- `release` (a reserved query given back, never below zero), `addInspected(events)` (adds, returns the counters),
  `get(grantId, periods)` and `getMany(grantIds <= 50, periods <= 4)` (one bounded read), `purgeBefore(updatedBefore, limit)`
  (housekeeping: `purgeGrantUsage` is run by the Worker's cron and `serve`'s timer for rows idle 120 days).
- Period keys are validated (`PERIOD_RE`), values are bound parameters. A quota is validated by `isStoredQuota` (auth
  `checkQuota`, the resolver, the import) and the HTTP layer (zod); the resolver fails closed (`invalid_config`) on a stored
  quota that is not well formed. On Workers the same interface is implemented by the `quota:<grant>` Durable Object
  (`createDurableQuotaStore`, falls back to this table).

### KV

Workers-KV semantics for the OAuth provider on Node (ADR-0009): `get`, `put(key, value, { expiration (epoch s) |
expirationTtl (s) })`, `delete`, `list({ prefix, limit ≤ 1000, cursor })` in key order. Expired keys are invisible.

## Adapters

| Adapter | Where | Notes |
|---|---|---|
| `memory` | `src/memory.ts` | Reference implementation; enforces every unique, FK and row rule; tests and ephemeral servers. |
| `yaml` | `src/yaml.ts` | Read-only view of `relic-bridge.yaml`: each project → project (id = slug) + credential (id `project:<slug>`). The stdio CLI resolves its project from `yamlRecords()` (synchronous) at startup. |
| `sqlite` | `packages/storage-sqlite` (`openSqliteStorage`) | Node, `node:sqlite` (ADR-0006). Creates the file `0600`, WAL, `busy_timeout`, `foreign_keys = ON`, runs `migrate()` on open (`migrate: false` only verifies). `backup(dest)` / `backupDatabase(src, dest)` write a consistent `0600` snapshot. Bundled into the CLI from source. |
| `d1` | `src/d1.ts` (`@relic-bridge/storage/d1`, `createD1Storage`) | Workers, on the `DB` binding (P3-02). Plain parameterised SQL like `sqlite`; every write is one statement (see below). Runs `migrate()` on open; `apps/worker` opens it once per isolate during the lazy boot. Contract and D1-specific tests run inside workerd (`apps/worker/test/d1.test.ts`, `pnpm test:workers`). |

Every adapter must pass the contract suite:

```ts
import { runStorageContract } from '@relic-bridge/storage/testing';

runStorageContract({
  name: 'sqlite',
  create: (clock) => openSqliteStorage({ path: ':memory:', now: clock.now }),
});
// read-only adapters: runStorageContract({ name: 'yaml', createSeeded: async (fixture, clock) => … })
```

### D1: atomic without transactions

D1 has no interactive transactions, and each call is a round trip other isolates can interleave with, so the adapter
never reads, decides in JavaScript, then writes. Every write is **one statement** whose condition the engine checks,
and the outcome comes from `meta.changes` or `RETURNING`:

- `settings.setIfAbsent`: `INSERT … ON CONFLICT(key) DO NOTHING`, `true` iff one row changed.
- `credentials.update` with `ifKey`: the guard is in the `UPDATE … WHERE` (`key_ciphertext`, `key_iv`, `key_version`).
  When nothing matched, one extra read tells `ConflictError` (`credentials.key`) from `NotFoundError`.
- Every `update`: `UPDATE … SET <patched columns only> … RETURNING *`, so concurrent patches of different fields both
  stick, and the result costs no extra read. `create` uses `INSERT … RETURNING *`.
- Cascades and restrictions are the engine's foreign keys. D1 always enforces them (`PRAGMA foreign_keys` reads 1; no
  pragma needed).
- Engine errors (`D1_ERROR: UNIQUE constraint failed: users.email: SQLITE_CONSTRAINT`, also in `cause`) map to the
  storage errors by constraint name (`mapD1Error`); values never reach the message.

### One-call access resolution (`loadAccessRecords`, P3-09)

Round trips matter on Workers. `Storage.loadAccessRecords({ tokenHash, projectSlug })` is an **optional** capability
that returns every row one access decision needs (`AccessRecords`: token, project, grant, grant user, credential,
credential owner) in one storage call. The SQL is written once, in `src/access-records.ts` (`ACCESS_RECORDS_SQL`,
one `SELECT` per field, bound parameters only), and run as:

- **D1**: one `batch()` — one round trip, one read transaction (a consistent snapshot);
- **SQLite**: the same statements inside one `BEGIN … COMMIT` read transaction.

`memory` and `yaml` don't implement it; `authenticateAccess` in `@relic-bridge/auth` then reads repository by
repository (`verifyAccessToken` + `resolveAccess`, unchanged). The contract (checked by `runStorageContract({ …,
accessRecords: true })`, required for SQL adapters):

- an unknown token hash → every field `null`;
- `project` by slug (`null` slug → `null`), `grant` = the token's grant;
- `user`, `credential` and `credentialOwner` only when the grant belongs to that project (THREAT_MODEL T2), with
  `credential = grant.credentialId ?? project.defaultCredentialId` and the owner only when it is not the grant's user;
- rows come back as stored (revoked, expired, disabled): the caller decides.

Cost on Workers: an access-cache miss is **one** D1 call (the batch) plus the throttled `last_used_at` write in the
background (`waitUntil`, at most once per token per 5 minutes); a hit costs none (`apps/worker/test/entry.test.ts`).
Before P3-09 a miss made five reads in three round trips. The `last_used_at` write stays separate on purpose: putting
it in the batch would make every miss a write transaction on the D1 primary, for a value that changes once per
5 minutes. A property test (`packages/auth/test/access-equivalence.ts`, run on SQLite in `apps/cli/test` and on D1
in `apps/worker/test/d1.test.ts`) checks that both paths reach identical decisions.

## Schema and migrations

1. Edit `packages/storage/src/schema.ts`.
2. `pnpm db:generate` — runs `drizzle-kit generate` (new `migrations/NNNN_*.sql` + snapshot) and
   `scripts/gen-migrations.ts`, which embeds the SQL into `src/migrations.generated.ts` (Workers can't read files).
   `pnpm lint` fails if the embedded copy is stale.
3. Commit both. Never edit an applied migration: the runner stores a SHA-256 checksum per migration and refuses a
   database whose applied migration differs.

`migrate(driver, MIGRATIONS)` (`src/migrate.ts`) needs only `all(sql, params)` and an atomic `batch(statements)`
(a transaction on Node, a D1 batch on Workers). It is:

- **idempotent** — applied versions are skipped, so it runs on every start;
- **forward-only** — no down migrations; a database newer than the build is refused;
- **atomic per migration** — the statements and the `schema_migrations` row commit together.

**On D1** the same runner and the same embedded `MIGRATIONS` are the only migration path (no `wrangler d1
migrations` directory, which would be a second history to keep in sync; ADR-0006 update P3-02). `createD1Storage`
runs it when the Worker's runtime boots, so a deploy migrates on its first request. Isolates booting at once on an
outdated database race safely: a loser's batch rolls back (primary key on `schema_migrations`, or its DDL) and it
re-runs from the versions now recorded, a bounded number of times. `PRAGMA foreign_keys` statements (drizzle-kit adds
them around table rebuilds) are skipped by the D1 driver: SQLite ignores them inside a transaction, and a D1 batch is
one. A migration that rebuilds a referenced table must keep its rows valid at commit (`PRAGMA defer_foreign_keys` is the
D1 tool if a future migration needs it).

`test/sqlite/migrate.test.ts` checks all of this against a real SQLite engine (`node:sqlite`, test only) and compares
the migrated tables, indexes and foreign keys with the Drizzle schema (drift check).

### Upgrade tests from published releases (P8-05)

A database created by any published release must open with the current build ([versioning
policy](../guide/versioning.md#database-upgrades-are-tested)). `test/fixtures/db/v<minor>.json` holds one database per
published minor, generated by `scripts/gen-db-fixtures.ts` (`pnpm db:fixtures`):

1. it reads `packages/storage/src/migrations.generated.ts` from the newest `v<minor>.<patch>` tag with
   `git show`, so the migrations are exactly the ones that release shipped;
2. applies them with `migrate()` to an empty `node:sqlite` database and inserts the fixed synthetic `SEED` (every table,
   fake ciphertext, made-up token hashes and account ids);
3. dumps the result as plain SQL: schema in creation order, then rows, parents first, columns by name.

`test/upgrade.ts` loads each fixture and checks it after opening with the current build: on SQLite
(`packages/storage-sqlite/test/upgrade.test.ts`, through `openSqliteStorage` on a file) and on D1 in workerd
(`apps/worker/test/d1-upgrade.test.ts`, through `createD1Storage`): every current migration applied with the current
checksums, the schema identical to a fresh database, the seeded rows read back through the repositories (and
`loadAccessRecords`), a write after the upgrade, and `migrate: false` refusing a database that is behind.

`node scripts/gen-db-fixtures.ts --check` runs in `pnpm lint`. It re-derives every dump from the migrations recorded in
the fixture (a hand edit fails) and checks that each recorded migration is still in this build unchanged. With release
tags present (not in a shallow CI checkout) it also checks the recorded migrations against the tags, that every
published minor has a fixture, and that no patch release changed migrations. After releasing a minor that adds a
migration: `git fetch --tags && pnpm db:fixtures`, add the new file to `DB_FIXTURES` in `test/upgrade.ts`, commit.
Changing `SEED` regenerates every fixture; extend `expectSeededRows` with it.
