# Cryptographic inventory

Every key, secret, algorithm and random source relic-bridge uses, with where it comes from, where it is kept, how long
it lives and what to do when it leaks. Written for [OWASP ASVS 5.0](asvs-l2.md) V11.1.1 and V11.1.2. Every row was
checked against the code (file and function named in the row), not copied from comments or other documents.

**Reviewed:** 2026-10-15 (P8-71), against `main` at 0.11.0. Review again when a row's file changes, when a dependency
in the [third-party section](#third-party-cryptography) changes major version, and before each minor release.
`scripts/test/crypto-inventory.test.ts` fails when a file starts using a cryptographic primitive or names an algorithm
that this document does not mention.

Paths are relative to the repository root. "Node" is `relic-bridge serve`, stdio and the CLI; "Workers" is the
Cloudflare Worker.

## Principles

- **One implementation:** WebCrypto (`crypto.subtle`, `crypto.getRandomValues`, `crypto.randomUUID`) on Node and
  Workers alike (ADR-0004). The only exceptions are Node-only tooling (`node:crypto` in one CLI command and three
  build scripts, listed [below](#random-sources)) and two libraries: `jose` 6.2.12 (JWT verification) and
  `@cloudflare/workers-oauth-provider` 1.2.1 (OAuth server tokens).
- **No secret is derived from a password** except the config-bundle passphrase (PBKDF2, run in the CLI only).
- **Hashes at rest, not plaintext:** every bearer value relic-bridge issues (device tokens, sessions, setup links,
  sign-in state, task ids, OAuth tokens) is stored as SHA-256. An unkeyed hash is enough because each input is a
  uniformly random value of at least 128 bits (192 to 256 in practice): no dictionary or brute force applies.
- **Constant-time comparison** (`packages/auth/src/crypto/bytes.ts` `timingSafeEqual`) for key check values, token
  hashes, session CSRF tokens, the sign-in binding cookie, the OIDC `nonce` and the admin token digest.
- **No custom primitives.** The only hand-written routines are the CRC-32 typo checksum of `rb_` tokens (not a security
  control) and `timingSafeEqual` (a comparison, not a primitive).

## Keys derived from the master key

`deriveVersionKeys` (`packages/auth/src/crypto/keyring.ts`) imports each master key version as an `HKDF` key and
derives, with HKDF-SHA-256, salt `relic-bridge/master-key/v1` and one `info` label per purpose (changing any label
changes every derived key: they are a storage format):

| Derived key | `info` label | Algorithm | Protects | Used in | Lifetime |
|---|---|---|---|---|---|
| Credential data key | `relic-bridge/credential-key/aes-256-gcm` | AES-256-GCM, non-extractable | New Relic keys in `credentials` | `Keyring.encryptCredentialKey` / `decryptCredentialKey` | One per master key version. |
| Key check value (KCV) | `relic-bridge/key-check` | 256 bits from `deriveBits` (not a key) | Detects a wrong master key at boot, before any row is touched | `packages/auth/src/crypto/rotate.ts` (`verifyKeyChecks`, constant-time compare); stored base64 in `settings` as `crypto.key_check.v<N>` (written once with `setIfAbsent`) | One per version; non-secret (a one-way HKDF output). |
| Audit identity key | `relic-bridge/audit-identity/hmac-sha-256` | HMAC-SHA-256, sign only | `identityHash` of a refused or unbound sign-in in audit rows: `v<N>.<base64url of the first 128 bits>` over the length-prefixed `(idp, subject)` | `Keyring.identityHash`, called from `packages/http-app/src/identity.ts` | Current version only: rotating the master key changes every new hash (the `v<N>` prefix says which ones compare). |
| Query cache id key | `relic-bridge/query-cache-id/hmac-sha-256` | HMAC-SHA-256, sign only | Opaque cache entry ids (THREAT_MODEL T16) | `packages/core/src/cache/query-cache.ts` (`QueryCache.idFor`), wired in `apps/cli/src/serve.ts` and `apps/worker/src/worker.ts` | Current version only; rotation starts a fresh cache. stdio has no master key and uses a random per-process HMAC key (`crypto.subtle.generateKey`). |
| Query cache data key | `relic-bridge/query-cache-data/aes-256-gcm` | AES-256-GCM | Bodies in the shared Workers Cache API (`RB_QUERY_CACHE=on`) | `CacheApiQueryCacheStore` (`query-cache.ts`), `createWorkerQueryCache` | As above. In-memory stores keep plaintext in process memory only. |

## Data encryption

All AES-GCM below uses a 96-bit IV and a 128-bit tag. relic-bridge's own sealing draws a fresh random IV for every
encryption; the OAuth provider uses a fixed IV with a fresh key for every encryption (see
[third-party](#third-party-cryptography)).

| What | Key | AAD | Stored form | File and function |
|---|---|---|---|---|
| New Relic key in `credentials` | Credential data key of the current version | `u32 len ‖ "relic-bridge/credential-key/v1" ‖ u32 len ‖ credential id ‖ u32 key version` (length-prefixed, so injective) | `key_ciphertext` (ciphertext ‖ tag), `key_iv` (12 bytes, CHECK constraint), `key_version`; plaintext ≤ 4096 bytes, no lone surrogates | `packages/auth/src/crypto/keyring.ts` (`credentialAad`, `seal`, `open`, `encryptCredentialKey`, `decryptCredentialKey`) |
| Config bundle keys | Wrap key = PBKDF2-HMAC-SHA-256 of the NFC passphrase, 600 000 iterations (accepted 600 000 to 10 000 000), 16-byte random salt, 32-byte output | `u32 len ‖ "relic-bridge-config/v1/secrets\|<kdf name>\|<iterations>\|<salt>\|" ‖ u32 len ‖ canonical JSON of each credential's ref, label, region, owner` | `secrets: {kdf, cipher: "aes-256-gcm", nonce, sealed}` in the bundle file | `packages/auth/src/transfer/seal.ts` (`newKdf`, `deriveWrapKey`, `sealCredentialKeys`, `openCredentialKeys`). The derivation runs in the CLI; a `--remote` server receives only the 32-byte wrap key over the admin API (`parseWrapKey`), so a Worker (whose WebCrypto caps PBKDF2 at 100 000 iterations) never runs the KDF or sees the passphrase. |
| Cached query results (Workers Cache API) | Query cache data key | `"relic-bridge/query-cache/v1:" ‖ entry id` | `IV ‖ ciphertext ‖ tag` in the per-colo cache; a body that fails to open is a miss | `packages/core/src/cache/query-cache.ts` (`CacheApiQueryCacheStore.get` / `put`) |
| MCP task records | AES-256-GCM key from HKDF-SHA-256 of the 256-bit task id (salt `relic-bridge mcp task v1`, info `aes-256-gcm`) | The task owner string (project, grant, token or OAuth device; pass-through key id and region) | `kv` row `SHA-256(task id)` → `v1.<iv>.<ciphertext>`, 15 min | `packages/core/src/tasks.ts` (`newTaskId`, `storeKey`, `recordKey`, `seal`, `unseal`) |
| OAuth refresh replay records | AES-256-GCM key from HKDF-SHA-256 of the presented refresh token (salt `relic-bridge oauth refresh replay v1`, info `aes-256-gcm`) | User, provider grant and token hash | `kv` row `oauth-refresh-replay:<SHA-256(token)>` → `v1.<iv>.<ciphertext>`, for the reuse window (default 30 s, at most 120 s) | `packages/http-app/src/oauth/refresh-replay.ts` (`replayKey`, `sealReplay`, `openReplay`) |

The importing Worker must run with the same master key (`cf:setup --master-key-stdin`). |

## OAuth authorization server

Tokens, codes and grants are created by `@cloudflare/workers-oauth-provider` 1.2.1 (read in
`node_modules/@cloudflare/workers-oauth-provider/dist/oauth-provider.js`); relic-bridge configures it in
`packages/http-app/src/oauth/server.ts` and stores its state in the `kv` table under `oauth:` (ADR-0011).

| Value | Generation (provider) | Stored as | relic-bridge additions |
|---|---|---|---|
| Access token, refresh token, authorization code | `<userId>:<grantId>:<secret>`; grant id 16 and secret 32 characters of a 64-symbol alphabet from `crypto.getRandomValues` (`generateRandomString`: 96 and 192 bits) | `token:<userId>:<grantId>:<SHA-256 hex>` and the grant's `authCodeId` / `refreshTokenId` (SHA-256 hex, `generateTokenId`) | Access 1 h, refresh 30 days by default (`DEFAULT_OAUTH_ACCESS_TTL_S`, `DEFAULT_OAUTH_REFRESH_TTL_S`), capped by the grant's expiry. Single-use code marker `SHA-256(code)` consumed with `kv.take` (`codeMarker`, 600 s); single-use refresh marker `SHA-256(token)` (`refreshMarker`); a reused refresh token outside the reuse window revokes the device. |
| Grant props (`grantId`, `projectSlug`, `userId`, `clientId`: no secrets) | Encrypted with AES-256-GCM under a fresh `generateKey` key per encryption and an all-zero 96-bit IV (`encryptProps`); safe because each key encrypts exactly once | Ciphertext on the grant and token records | — |
| Props key wrapping | AES-KW with a key = HMAC-SHA-256 over the token string under a constant key embedded in the library (`deriveKeyFromToken`, `wrapKeyWithToken`) | Wrapped key next to each token or code record | A database copy holds only token hashes, so it can't unwrap the props key. |
| PKCE | S256 only: the provider refuses `plain` (`codeChallengeMethods: ["S256"]`); relic-bridge also requires a challenge for every client, confidential ones included (`server.ts`, "PKCE with code_challenge_method=S256 is required") | Challenge on the grant | — |
| Dynamically registered client secret (confidential clients) | 32 characters, `generateRandomString` (192 bits) | SHA-256 hex on the client record | Refresh replays re-check it in `clientAuthenticates` (`refresh-replay.ts`), comparing SHA-256 hex digests with `===`: not constant time, but an attacker can't choose the digest of a guess, so timing reveals nothing usable. Most MCP clients are public (`token_endpoint_auth_method: none`) or CIMD. |
| Client ids | Dynamic: 16 characters (`generateRandomString`); CIMD: the client's https URL | `client:<id>` | `kv` markers keyed by `SHA-256(client id)` for CIMD bookkeeping and client removal (`server.ts`). |
| Remembered approvals | — | `kv` row `oauth-consent:<userId>:<base64url SHA-256 of [client id, redirect URI, resource]>` | `packages/http-app/src/oauth/consent.ts` (`approvalId`): an index, not a secret. The provider's HMAC-signed approvals cookie and encrypted consent transactions are not used. |

## Sign-in token verification

`packages/auth/src/identity/jwt.ts` (`verifyJwt`, `remoteKeySource`) on `jose` 6.2.12:

- **Accepted algorithms:** RS256, RS384, RS512, PS256, PS384, PS512, ES256, ES384, ES512, EdDSA, Ed25519
  (`ASYMMETRIC_ALGORITHMS`), intersected with what the IdP advertises in `id_token_signing_alg_values_supported`
  (`oidc.ts`, RS256 when absent). Cloudflare Access assertions: RS256 only (`cf-access.ts`). `none` is never accepted
  by jose and HMAC (`HS*`) is excluded, so a public key can't be used as a shared secret.
- **Claims:** exact `iss`, `aud` (client id or Access AUD tag; `azp` checked with several audiences), `exp`, `iat` at
  most 600 s old for ID tokens, `nonce`, 60 s clock tolerance, tokens over 16 KiB refused.
- **Keys:** the issuer's JWKS, cached 10 min per provider instance, refetched for an unknown `kid` at most every 30 s,
  no redirects, body size capped. Discovery documents cached 1 h (`DISCOVERY_CACHE_MS`).
- **GitHub** has no ID token: the identity comes from the API with a short-lived access token that is never stored
  (`github.ts`).

No asymmetric key is ever generated or used to sign by relic-bridge.

### Self-monitoring ids

`packages/http-app/src/telemetry.ts`: `service.instance.id` (16 random bytes per exporter), OTLP trace ids (16 bytes,
unless an accepted inbound `traceparent` supplies one) and span ids (8 bytes) all come from `crypto.getRandomValues`
(`hex`). `Math.random` (`TelemetryOptions.random`) only decides whether a tool call is sampled as a span
(`RB_OTEL_SAMPLE`); predicting it gains nothing.

## Transport security

relic-bridge does no TLS of its own and handles no certificates.

- **Inbound:** `serve` speaks plain HTTP and expects a TLS proxy for anything beyond the machine
  ([self-hosting](../guide/self-hosting.md), `deploy/Caddyfile`); the Worker is HTTPS through Cloudflare. TLS versions and
  cipher suites belong to that layer (ASVS V12.1.1, V12.1.2).
- **Outbound:** NerdGraph endpoints are fixed `https://` URLs (`packages/core/src/nerdgraph/endpoints.ts`); IdP
  discovery, token and JWKS endpoints must be https (http only for a loopback IdP in development, `oidc.ts`
  `checkEndpoint`); CIMD documents are https on port 443; the OTLP endpoint must be https (http only for localhost,
  `telemetry.ts`). Certificate validation is the runtime's (Node's bundled CA store, Cloudflare's for Workers); nothing
  turns it off.

## Not used, on purpose

- **Password hashing (bcrypt, scrypt, Argon2):** there are no passwords; sign-in is delegated. PBKDF2 is used only for
  the config bundle passphrase, in the CLI (the owner chose it over Argon2id to stay on WebCrypto, P7-06).
- **A pepper or HMAC for token hashes:** inputs are uniformly random ≥ 128-bit values (ADR-0009).
- **ECB, CBC, CTR, RSA encryption, PKCS#1 v1.5 encryption, MD5, SHA-1, DES, RC4, HS256:** none appear.
- **Asymmetric key generation and signing:** relic-bridge only verifies IdP signatures.
- **Self-issued JWTs:** OAuth tokens are opaque.
- **A wrapped data-encryption key per row:** keys are derived from the master key with HKDF, so there is no key table to
  lose or leak (ADR-0007).
- **Custom TLS or certificate pinning.**
